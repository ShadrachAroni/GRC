# GRC Sentinel - Operational Administration Manual

This manual provides instructions for deploying, managing, and maintaining the infrastructure of the GRC Sentinel application.

---

## 1. System Boot Operations (Docker Compose)

The entire application stack is containerized and can be launched using Docker Compose.

### Step-by-Step Launch Procedure

1. **Environment Configuration**: Verify that a `.env` file exists in the root folder. You can copy variables from `.env.example` as a starting template.
2. **Build and Run Containers**:
   ```bash
   docker compose up --build -d
   ```
3. **Verify Health Status**:
   ```bash
   docker compose ps
   ```
   Both the `api` and `frontend` services expose health endpoints (`/health` on backend) and will only be marked healthy when they pass connectivity checks.
4. **Stop Services**:
   ```bash
   docker compose down
   ```

## 2. Database Bootstrapping & Seeding

The application dynamically supports **SQLite** (default for local development) and **PostgreSQL** (for production deployments), configured via the `DATABASE_URL` setting.

### Seeding Initial Data
To populate the database with baseline compliance frameworks, mapping controls, and mock risks:
1. Ensure the Python virtual environment is active.
2. Run the database seed script:
   ```bash
   python data/seed_db.py
   ```
   This script loads JSON baseline definitions from `data/seed_controls.json` and `data/seed_risks.json` and saves them to the active database.

## 3. Database Schema Migrations (Alembic)

Database schema updates are managed using Alembic. Tables are automatically initialized on startup, but production schema updates are managed via Alembic.

### Common Migration Actions
- **Apply Outstanding Migrations**:
  ```bash
  alembic upgrade head
  ```
- **Autogenerate a Migration File**:
  After updating models inside `api/models.py`, generate a new revision script:
  ```bash
  alembic revision --autogenerate -m "Add new columns"
  ```
- **Rollback Last Migration**:
  ```bash
  alembic downgrade -1
  ```

## 4. Cryptographic Key & Secret Rotation Policy

To comply with corporate security standards, secrets must be rotated every 90 days.

### Steps to Rotate secrets

- **JWT Secret Key**:
  1. Generate a new secure 256-bit hexadecimal string:
     ```bash
     openssl rand -hex 32
     ```
  2. In your `.env` file, update the `JWT_SECRET_KEY` variable.
  3. Restart the API service:
     ```bash
     docker compose up -d --no-deps api
     ```

- **Stripe Webhook Secret**:
  1. Retrieve the new webhook secret from the Stripe dashboard.
  2. Update the `STRIPE_WEBHOOK_SECRET` in `.env`.
  3. Restart the API service.

- **Flutterwave Verification Hash**:
  1. Define a new unique webhook signature key.
  2. In `.env`, update the `FLUTTERWAVE_WEBHOOK_SECRET` value.
  3. Update the matching custom hash setting inside your Flutterwave account dashboard.
  4. Restart the API service.

## 5. Disaster Recovery & Backups

### PostgreSQL Backups (pg_dump)
- **Create a Backup**:
  ```bash
  docker compose exec -t db pg_dump -U grc -d grcdb -F c -b -v -f /var/lib/postgresql/data/backup.dump
  docker compose cp db:/var/lib/postgresql/data/backup.dump ./backups/grcdb_backup_$(date +%Y%m%d).dump
  ```
- **Restore a Backup**:
  ```bash
  docker compose cp ./backups/my_backup.dump db:/var/lib/postgresql/data/restore.dump
  docker compose exec -t db pg_restore -U grc -d grcdb --clean --no-owner /var/lib/postgresql/data/restore.dump
  ```

### SQLite Backups (Local Dev)
- Simply copy the active sqlite database file (e.g. `grcdb.db`) to a secure backup directory while no write transactions are occurring.

## 6. SIEM JSON Log Ingestion

All structured events generated by the audit logger are appended to the application standard output (stdout) or redirected to:
`/var/log/grc_sentinel/audit.log`

Ingestion agents (like Splunk Forwarder, FluentBit, or Logstash) should be configured to parse this file as raw JSON.
